\textbf{Three-way agreement.} Every layer's cycle count is identical in the
model, in RTL simulation (xsim) and on the KV260 (Fig.~\ref{fig:cycles}).
On the board each layer took a single cycle count over all 10,000 test
images of each network, as in the full-dataset RTL simulation. % src: tab_a3_cycles; tab_layer_spread (1 distinct value); hw_a2_a3_cycles.csv hw_stall_max 0, hw_shapes.csv hw_stall 0 (300 jobs), hw_soak.csv stall_nonzero 0
On the board, all 286 legal random-shape jobs are bit- and cycle-exact and
all 14 illegal ones are refused (Fig.~\ref{fig:shapes}). Cycle counts are
also identical at all 7 clocks of a 100--250\,MHz sweep.

\textbf{Correctness.} The board's logits differ from the golden model on 0
of 10,000 images per network, so its accuracy equals the INT8 reference:
98.79\,\% and 78.52\,\%. A 30-minute soak ran 3.65M inferences with no
error and one cycle count per network. % src: tab_a1_accuracy; tab_soak

\textbf{Latency.} Compute takes 65.7 and 417.0\,$\mu$s per image, with no
spread across images or sessions: 15,210 and 2,398 images/s, 39.6\,\% and
67.3\,\% of the 32 GOPS peak, which equals the PE utilization of
Sec.~\ref{sec:model}. % src: tab_a5_cpu (65.7 [65.7, 65.7]; 417.0 [417.0, 417.0]); tab_efficiency (img/s; pct of peak 39.6 / 67.3; peak 32.0)
The Python host adds most of the end-to-end time: median 224.5 and
578.5\,$\mu$s, p99 239.1 and 593.2\,$\mu$s. Determinism therefore holds for
accelerator compute; the end-to-end spread comes from the host.
% src: tab_compare; tab_percentiles (fast host path p99)

\textbf{Comparison.} Against the best CPU baseline, ONNX Runtime INT8 with
4 threads, the accelerator is 3.10$\times$ and 2.11$\times$ faster end to end
(Table~\ref{tab:compare}). The CPU's end-to-end time also includes input
preprocessing; on compute alone the ratio is 9.41$\times$ and 2.58$\times$.
% src: tab_compare; tab_a5_cpu (comp. speedup 9.41x / 2.58x; preprocessing note)
The accelerator is 1.5$\times$ faster than the DPU on LeNet-5, while the DPU
is 1.6$\times$ faster on CIFAR-10. The DPU's own runner time is 195.0 and
182.4\,$\mu$s, so on CIFAR-10 its compute is shorter than ours as well; it
runs a different INT8 quantization of the same networks.
% src: tab_a5_cpu DPU/accel e2e 1.54x / 0.61x (PAPER_PLAN 1.5x faster / 1.6x slower); DPU runner p50 195.0 / 182.4 (tab_a5_cpu, tab_percentiles)

\textbf{Power and energy.} SOM-rail power (INA260) idles at 3.207\,W with
no overlay, 3.44\,W with our design loaded and 4.36\,W with the DPU's.
Per image, the accelerator uses about half the DPU's energy on LeNet-5
(0.065 vs.\ 0.124\,mJ), a comparable amount on CIFAR-10 (0.161 vs.\
0.166\,mJ), and 5.5--7$\times$ less than the CPU.
% src: tab_power_compare (3.207; 3.442 / 3.433; 4.362 / 4.361); tab_compare (energies; CPU 0.454 / 0.895 -> 6.98x / 5.56x)
Most of our $\Delta P$ is the host loop: running the same loop without
starting the accelerator already adds 0.222 and 0.211\,W of the 0.251 and
0.263\,W, so the $\Delta P$ attributable to the PL work is 29.0 and
51.4\,mW (Table~\ref{tab:compare}). % src: tab_b1_power (dP control 0.222 / 0.211; dP accel 0.251 / 0.263); tab_compare note (accel_dp_net_w median 29.0 / 51.4 mW)

\textbf{Repeatability and clock.} Across sessions the end-to-end medians stay
within [223.3, 225.4] and [576.9, 580.5]\,$\mu$s, and energy per image varies
by a CV of 3.0\,\% and 0.4\,\%. Latency scales as $1/f$ with constant cycles,
and power fits $P = 3.424\,\mathrm{W} + 1.095\,\mathrm{mW/MHz} \cdot f$
($R^2 = 0.9964$); a second sweep gave a slope 8\,\% different.
% src: tab_repeatability (B3 e2e fast [223.3, 225.4], [576.9, 580.5]); tab_b1_power (E_sys CV 3.0 / 0.4); tab_b2_fit

\textbf{Lessons learned.} Cycle-exact results cannot reveal a wrong clock:
the first board session ran the 300\,MHz build at 199.998\,MHz, because
PYNQ does not program the design's PS PLLs, and every check passed. The
driver now sets the PL clock after each overlay load and fails unless the
read-back matches, which showed that the board's PLLs cannot produce
300\,MHz. A power sampler running as a Python thread was starved by the
interpreter lock (1--14 samples in 20--30\,s instead of 10\,Hz); a separate
process restored about 10\,Hz. Session-end overlap checks flagged power
phases disturbed by SSH logins (up to +15\,mW on a phase mean) and by an
unattended OS update inside one clock sweep, which was re-run. Random-shape
testing exposed the unchecked kernel-width limit (Sec.~\ref{sec:verif}).
