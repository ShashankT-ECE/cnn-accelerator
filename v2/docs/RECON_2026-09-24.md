## 4. Cycle model

**Where the models are:**
- **Generalized model:** `python/v2_architecture_model.py`. It reproduces **30,013 and 225,584 exactly**.
- **Tests:** `python/tests/test_v2_architecture_model.py` has **40 checks, not 41**, and all 40 pass. It is a plain script with no `test_` functions. No doc mentions 41.
- **V1 uniform model:** `python/mapping_model.py` and `python/cifar10_mapping_model.py`. They reproduce OS 43,021 / WS 140,412 and 279,664 / 893,460.

**Mapping.** Rows are output channels and columns are 8 consecutive output x positions in one output row (`v2_architecture_model.py:153`). That is your V2 layout rotated 90°, and the tile count equals your T in all 9 layers.

The array's inner loop is the V1 schedule: IC·K separate passes, one per kernel row (`:81`). Each pass streams K taps through one shared activation shift chain.

Conv group cost is `1 + IC·K·(P+K) + 2·rows` (`:75-98`), which breaks into:
- **core:** IC·K·K
- **lead-in:** IC·K·(P−1), refilling the shift chain before every pass
- **pass drain:** IC·K
- **clear:** 1
- **result drain:** 2·rows

FC cost is `ceil(OC/8)·(IC+2) + 2·OC` (`:119-124`). This FC schedule is verified bit-exact in RTL simulation.

**Not modeled:** pooling, ReLU, requant (these run on the PS), DDR or activation loads, and control start-up. The weight-BRAM stall is fixed at 0 by assumption (`:29-33`).

The V1 uniform model charges a full 8-pixel lead-in and a 16-cycle drain even on partial groups. That overcharge is exactly why V1 is higher than the generalized model.

**Reconciliation.** Your V2 arithmetic is correct in every layer. The core column equals your V2 compute layer by layer, so **"different mapping/tiling" contributes 0 cycles**. The whole gap is overhead.

In the table below, (a\*) means overhead caused by the V1 per-pass schedule, which V2's continuous stream of IC·KH·KW removes. (b) is overhead V2 hides, (c) is overhead V2 also pays.

| Layer | Delta | (a\*) lead-in + pass drain | (b) drain + clear, hidden | (c) FC tail |
|---|---|---|---|---|
| L conv1 | 5,376 | 3,920 | 1,456 | – |
| L conv2 | 6,680 | 6,000 | 680 | – |
| L conv3 | 1,455 | 1,200 (possible bug, below) | 255 | – |
| L fc1 / fc2 | 190 / 24 | – | 179 / 22 | 11 / 2 |
| **LeNet** | **13,725** | **11,120** | **2,592** | **13** |
| C conv1 | 54,656 | 47,040 | 7,616 | – |
| C conv2 | 65,360 | 64,000 | 1,360 | – |
| C conv3 | 1,416 | 1,280 | 136 | – |
| C fc | 24 | – | 22 | 2 |
| **CIFAR** | **121,456** | **113,600** | **9,134** | **2** |

- **(a\*):** V2 only avoids this if it can feed 8 different activations per cycle from on-chip buffers. That is an open design item.
- **(b):** the clear is only hidden if V2 loads the first product straight into the accumulator. No spec says whether it does, so those 180 / 538 cycles might belong in (c).
- **(d) possible model bug:** the conv formula charges one drain cycle per pass, but the FC schedule doesn't. The P=1 layers (LeNet conv3, CIFAR conv3) have only analytical support, not RTL.

**Missing from your V2 compute counts:** the pipeline fill/skew that V2 will still pay. V2's skew isn't specified anywhere, so assuming 8–15 cycles per tile:
- LeNet: +1,440 to 2,700 cycles (+8.8 to 16.6%)
- CIFAR: +4,304 to 8,070 cycles (+4.1 to 7.8%)

If fills overlap across tiles, this drops to about one fill per layer. Each layer's last result drain also can't be hidden: +40 cycles for LeNet, +32 for CIFAR.

## 5. Risks for a V2 build in `v2/`

1. **Requant contract.** Neither reference has an integer (M0, shift) requant; both use float64 × M with round-half-to-even. Before writing V2 RTL, the team needs to agree on a fixed-point requant and a rounding rule, update the Python reference to match, and re-check accuracy. The spec text and `requantize_fixed` disagree on rounding, so neither can be copied as is.
2. **The CIFAR reference isn't frozen.** It is untracked, has no INT8 parameters on disk, no golden vectors and no manifest. Right now, V2 CIFAR results have nothing bit-exact to compare against.
3. **Most of the current state is uncommitted,** including Phase 3, CIFAR, the frozen LeNet mapping manifest, and the `sparsity_disable` change that `cnn_axi_ctrl` needs. Committed HEAD doesn't elaborate `cnn_axi_ctrl`. Branching V2 off HEAD would lose all of this.
4. **The final layer uses float.** Logits are dequantized to float32 before argmax. V2 hardware will almost certainly take argmax on int32 accumulators. That gives the same prediction in most cases, but a tie or a near-tie across channels with different scales could pick a different class. The team needs to decide which is the reference.
5. **Accumulators include the bias differently.** `layer_vectors.npz` stores int64 accumulators *without* bias; the hardware accumulator is int32 (Decision 2). V2's testbenches need to compare the same quantity.
6. **No reusable build infrastructure.** There is no XDC, `.xpr` or bitstream outside the gitignored `build/`, and the board Tcl has never run. V2 needs its own tracked constraints and scripts.
7. **Tool gaps.** `pytest` isn't installed, and 30,013 appears only in untracked files. `run_verification.sh:21` writes xsim output into the repo root. A `v2/` flow should run xsim in its own build directory.
8. **Placement vs CLAUDE.md.** CLAUDE.md asks not to add unnecessary new top-level directories, and a `v2/` folder is one. It probably needs an explicit team decision recorded in `PROJECT_STATE.md`.

## LeNet-5 (frozen L1 in commit 16ef0e8, frozen L2 in commit 01049a8)

**B1. q_bias**
- Code at `reference/quant.py:70-73`: `q = rne(b / (s_a * s_w))` then `return q.astype(np.int32)`.

**B2. M**
- Computed at `int8_model.py:137` (and 150, 163, 176): `"M": S_in * S_w / S_out`. `S_in`/`S_out` are Python floats (`quant.py:36`) and `S_w` is a float64 ndarray (`quant.py:44-47`), so M is **float64**, one value per channel.

**B3. Requant expression**
- `int8_quant.py:33-34`: `q = rne(np.asarray(y, dtype=np.float64) * np.asarray(M, dtype=np.float64))`, then `np.clip(q, -128, 127).astype(np.int8)`.
- Dtypes step by step:
  - The accumulator is int64, from `int_conv2d`'s `astype(np.int64)` at `int8_model.py:88,90`.
  - Adding the int32 bias gives int64.
  - The multiply by M is done in **float64**.

# Appendix C — Cycle model reconciliation (verbatim)

The generalized model reproduces 30,013 (LeNet-5) and 225,584 (CIFAR-10) exactly, and the V1 model reproduces 43,021 / 140,412 and 279,664 / 893,460. The one thing that doesn't match your brief is the test count: the suite has **40 checks, not 41**, and all 40 pass. Nothing in `docs/` mentions "41".

The main finding is that the generalized model uses the same tiling as your V2 plan, tile for tile. None of the extra cycles comes from a different tiling. It all comes from how the old array runs each tile, and most of it goes away with V2's streamed-K design.

## 1. Where the models are

- **Generalized OS model:** `python/v2_architecture_model.py`. Its tests are in `python/tests/test_v2_architecture_model.py`. That file is a plain script: it has no `test_` functions and `pytest` is not installed in `.venv`. I ran it directly: 40 PASS, 0 FAIL, exit code 0. The totals are asserted at lines 82-83.
- **A second implementation** gives the same CIFAR number: `os_conv_refined` in `python/cifar10_mapping_model.py:135-154` also totals 225,584 (reported in `docs/CIFAR10_MAPPING_RESULTS.md:249`). It assumes 8 active rows per group (lines 151, 153), which is only correct because every CIFAR OC is a multiple of 8.
- **V1 uniform OS/WS model:** `python/mapping_model.py` (LeNet) and `python/cifar10_mapping_model.py` (CIFAR).
- **Layer names differ from yours:** the model's LeNet conv3 and conv5 are your conv2 and conv3.

## 2. How the models map layers to the array

**Array roles (both models):**
- The 8 rows are output channels and the 8 columns are 8 consecutive output pixels in one output row (`v2_architecture_model.py:153`, `docs/LENET5_MAPPING_SPEC.md:16`).
- Weights are broadcast along each row. Activations enter one shared stream and shift across the columns, arriving `c` cycles late at column `c` (`docs/FC_SCHEDULE_VALIDATION.md:12-15`).
- This is your V2 layout rotated 90°. The number of tiles is the same, and I checked that the model's group count equals your T for all 9 layers.

**Tiling:**
- **OC:** split into ceil(OC/8) channel groups; the last one has `rows = OC − 8g` active rows (`v2_architecture_model.py:105-107`).
- **Spatial:** each output row is split into `W//8` full column groups plus one partial group of `P = W mod 8` pixels, repeated for all H output rows (lines 108-114).
- **IC × K × K:** worked through in time as IC·K separate passes, one per kernel row (line 81). Each pass streams K taps through the column shift chain.

**Cost of one conv group:** `1 + IC·K·(P+K) + 2·rows` (lines 75-98). Split into terms:

| Term | Cycles per group | Meaning |
|---|---|---|
| MAC core | IC·K·K | the useful multiply-accumulates, identical to your V2 K |
| Per-pass lead-in | IC·K·(P−1) | refilling the shift chain before each kernel-row pass (line 82) |
| Per-pass drain | IC·K·1 | last product into the accumulator, paid after every pass (line 84) |
| Clear | 1 | accumulator clear plus first weight load (line 86) |
| Result drain | 2·rows | read-out at 2 cycles per row (line 87) |
| Weight-BRAM stall | 0 | assumed hidden by look-ahead addressing (lines 29-33); not RTL-verified |

**FC layers:** `ceil(OC/8)·(IC+2) + 2·OC` (lines 119-124). That is IC core cycles plus 1 clear plus 1 tail per group, plus the result drain. This schedule is RTL-verified bit-exact.

**V1 uniform model:** `17 + IC·K·(K+8)` for every conv group (`mapping_model.py:68`, `cifar10_mapping_model.py:85`). It forces P = 8 and 16 drain cycles on every group, so partial column groups and partial channel groups are overcharged. V1's FC formula is already the corrected one (`mapping_model.py:57`), so V1 and the generalized model give the same FC numbers.

**Not modeled by either:** pooling, ReLU and requantization (these run on the PS side, `docs/LENET5_MAPPING_SPEC.md:41-42`, `cifar10_mapping_model.py:41-42`). Also absent: weight and activation loads from DDR, bias, and any per-layer control/FSM start-up. The only load-related term is the weight-BRAM stall, and it is fixed at 0. So none of the gap to V2 comes from loads.

**What each class means here:**
- **(a)\* — V1's per-pass schedule, not tiling.** Each of the IC·K passes pays P−1 cycles to refill the single activation shift chain plus 1 un-pipelined drain cycle. That is 8 cycles per pass for a full group, and IC·K·8 is about 1.6× (LeNet conv1) to 0.32× (CIFAR conv3) of the core time. V2 streams all of IC·KH·KW continuously, so it pays this only once per tile. The price is bandwidth: V2 needs 8 distinct activations per cycle where V1 needs one stream. How V2 feeds 8 consecutive x per cycle from on-chip buffers is an open design item.
- **(b) — overhead V2 hides.** The result drain (2·rows per group) overlaps with the next tile, which works because every layer's K is at least 25, well above 8. The per-group clear goes away if V2 selects "load" instead of "accumulate" on the first product. Whether V2 does this is not specified anywhere, so the 180 (LeNet) / 538 (CIFAR) clear cycles might be (c) instead.
- **(c) — overhead V2 also pays.** The FC 1-cycle tail per group (product-to-accumulator latency). V2 also leaves the last tile's drain un-hidden in each layer: 8 cycles × 5 layers = 40 for LeNet and 8 × 4 = 32 for CIFAR.

## 5. Surprises and possible bugs

1. **The suite is 40 checks, not 41,** and pytest can't collect it: there are no `test_` functions and pytest isn't installed. The 9 BRAM checks (lines 94-97) only confirm a hard-coded constant, `latency_hidden_by_lookahead: True` (line 147). They don't verify anything in hardware.
2. **The conv and FC formulas disagree (possible (d)).** Plug K=1 and P=1 into the conv formula and each pass costs P+K = 2 cycles, giving 1 + 2·IC + 2·rows. The FC schedule costs 1 + IC + 1 + 2·rows. So conv charges a drain cycle after every pass, while FC passes run back-to-back. For the P=1 conv layers (LeNet conv5, CIFAR conv3), that per-pass drain is the entire 1,200 / 1,280-cycle non-drain overhead. It is RTL-anchored only by the IC=1, P=8 82-cycle measurement; the P=1 case is analytical.
3. **The weight-BRAM stall is fixed at 0 by assumption,** via look-ahead addressing that hasn't been implemented. Without it, the model says +1 cycle per group: +180 cycles for LeNet and +538 for CIFAR (the test at line 104 confirms +448 on CIFAR conv1).
4. **Pooling, ReLU and requantization cost 0 array cycles in both models** (PS-side). No DDR or activation-load cycles are modeled anywhere. None of this appears in the delta, and a real end-to-end number would need to add it.
5. **Only one conv number is RTL-verified:** the 82-cycle IC=1 anchor. Everything with IC > 1, OC > 8 or partial groups is analytical, as the model itself says (`timing_status`, lines 185-190).
6. **Minor issues:**
   - Layer names don't match your V2 names.
   - `os_conv_refined` hard-codes 8 active rows (`cifar10_mapping_model.py:151,153`); harmless for CIFAR.
   - 30,013 appears only in the untracked `data/benchmark/v2_architecture_results.json:131` and the test file, not in any doc.
