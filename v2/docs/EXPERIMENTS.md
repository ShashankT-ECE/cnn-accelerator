# V2 Experiment Plan

## Thesis
A small INT8 output-stationary accelerator with bit-exact end-to-end inference and cycle-exact agreement between the analytical model, RTL simulation, and measured KV260 execution.

## A — Core results
- **A1 Correctness:** full 10k test sets, both nets. Record images tested, output mismatches vs golden (target 0), golden accuracy, hardware accuracy.
- **A2 Latency:** per-layer and total PL cycles; µs at the implemented clock; wall-clock per image.
- **A3 Three-way cycle agreement per layer:** model_cycles, rtl_cycles, hw_cycles, rtl_err_pct, hw_err_pct.
- **A4 Utilization per layer:** MAC_ACTIVE/TOTAL, compared with the theoretical value.
- **A5 Same-board CPU baseline (Cortex-A53):** INT8 numpy and FP32. Protocol: warm-up discarded, median of ≥100 runs, 1 thread and 4 threads reported separately, numpy/BLAS version recorded. Split compute-only vs end-to-end on both CPU and FPGA (FPGA compute-only = PL counter; FPGA end-to-end = input write + start + poll + logit read).
- **A6 Implementation:** LUT/FF/DSP/BRAM, WNS, achieved clock.

## B — Power and system
- **B1 SOM-rail power (INA260):** primary measurement = the on-board INA260 on the SOM rail (VCC_SOM), sampled remotely on the board by `board/power_log.py` (hwmon `ina260*` node, else `platformstats -p`, else read-only I2C; backend, device and sensor update/averaging limits recorded) at a fixed requested rate (default 10 Hz); the achieved rate (samples / elapsed) and the max inter-sample gap are recorded.
  - **Protocol** (per net): idle 60 s → accelerator loop 60 s → idle 60 s → **control** 60 s → idle 60 s → CPU baseline 60 s, repeated 3×, plus one final idle 60 s = 19 phases ≈ 19 min per net (each phase with START/STOP banners; `--no-control` gives the earlier 13-phase protocol). Accelerator loop per image: `GosDevice.infer` (input write, pre-start clear, start, STATUS poll, LOGIT read; host path recorded), TOTAL_CYC read, PS dequant + argmax. **Control** = the same host loop with the accelerator **not started**: input write, the soft_reset + clear poll, a STATUS poll spin for the median start→done time of the preceding accelerator phase, LOGIT read, TOTAL_CYC read, PS dequant; STATUS ≠ 0 or TOTAL_CYC ≠ 0 aborts the step. ΔP_accel − ΔP_control therefore isolates what the PL compute adds on top of the host-loop activity (PS, DDR, AXI polling). CPU baseline = `cpu_int8_ref`, 1 thread.
  - **Report** per phase mean, std, n samples, rate, duration, images; per repeat and mean/std over the 3 repeats: P_idle (mean of the two idle phases bracketing the run phase), P_accel, P_control, P_cpu, ΔP = P_run − P_idle, time per image = phase duration / images, energy per image = ΔP × time per image; accelerator energy two ways: **E_sys** = ΔP_accel × wall time per image (host loop included) and **E_comp** = ΔP_accel × TOTAL_CYC / f (TOTAL_CYC = hardware counter, median over the phase's images; f = pl_clk0 read back); **duty cycle** = (TOTAL_CYC / f) / wall time per image; the control-subtracted variants ΔP_accel − ΔP_control, E_sys,net and E_comp,net — all computed by the script (`power_log.summarize`), never typed; paper table B1 shows them with placeholders until board data.
  - **Label** every number "SOM-rail power (INA260)": it is SOM-rail power, not accelerator-only power and not board input power. An external inline 12 V meter is optional and only a cross-check.
  - **Rail coverage** (board/README.md "VCC_SOM coverage (INA260)" has the verbatim quotes): UG1089 v1.3 (May 14, 2024), Ch. 2 "Powering the Starter Kit and Power Budgets": "The SOM power rail (VCC_SOM) is powered by the 5V supply" and "A power monitor device is available on the SOM power rail (VCC_SOM). You can access the total power consumed by the SOM module through the I2C bus"; "The carrier card provides the programmable logic (PL) the VCCO voltage rails". DS987 v1.0 (Apr 20, 2021): "SOC power supplies derived from a single +5V input", "PL I/O supplies customized through carrier card defined power rails", PS/PL VCCO rails "supplied by the carrier card". The upstream KV260 carrier device tree names `ina260@40` "ina260-u14" on the carrier I2C bus. So VCC_SOM = the SOM's +5 V input: everything on the SOM (PS incl. the Python host and the CPU baseline, PL core, and — inferred, not stated per rail — the on-SOM DDR4, flash and regulator losses), excluding the carrier-supplied VCCO rails and all carrier-side loads. Open: U14 = the VCC_SOM monitor per the carrier schematic; per-rail split (DS987 lists SOM "PL/PS power domain monitor" devices at 0x68/0x70, unused).
- **B2 Clock sweep 100/150/200 MHz + every higher variant that closed timing (250, 300 MHz; 2026-09-28, D14), capped at the deployed bitstream's closed clock; 250 MHz is the fallback bitstream:** latency, power, energy; cycle counts recorded as a consistency check. Runtime clock switching to be verified at bring-up; fallback one bitstream per clock. Power per clock uses the same INA260 SOM-rail logger (`board/power_log.py`, label "SOM-rail power (INA260)").
- **B3 End-to-end breakdown:** host-side phases per image with `time.perf_counter_ns` (≥ 1000 images, 50 warm-up discarded; median, p5, p95, p99): input write, status clear (soft_reset of the previous job's sticky done), start→done (= CTRL.start write + STATUS poll, also reported separately), LOGIT read, PS dequant, end-to-end (sum), counter read (measurement overhead, not in end-to-end), PL compute (TOTAL_CYC / f). Measured for **both host paths**: safe (per-word MMIO, `hw_b3_breakdown.csv`) and fast (PL windows mapped once, the input image as one vectorized numpy copy into ACT0, the 16 LOGIT words as one vectorized read, tight STATUS poll; `hw_b3_breakdown_fast.csv`). The fast path is used on the board only after its bring-up check (Session 1 `s1.fast`: whole ACT0 window written fast and read back word by word, CSR block reads == per-word reads, both nets bit/cycle-exact); otherwise it is not run and the safe path is the result. The paper table reports safe vs fast per phase and the end-to-end speedup (safe median / fast median, computed). A laptop MockMMIO comparison of the two host code paths (`board/exp_host_overhead.py`, `results/dryrun/host_overhead_mock.csv`, "host overhead, laptop mock (MockMMIO), not KV260") is a dry-run aid only and never a B3 result.
